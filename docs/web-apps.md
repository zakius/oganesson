# Installed web apps

## Links out of the app

A link in an installed web app's window that leads out of the app's scope opens in the system default browser, as a link from any other desktop app does. On Linux that is what `xdg-open` opens: the desktop's default web browser.

- **Which apps.** Installed web apps (PWAs), also DIY apps: a page installed with "Install page as app…", which opens in a window as well (on Linux, "Create shortcut…" only puts a desktop shortcut to the page, which opens in a tab). Not isolated web apps, and not extension-based hosted apps, which Chromium no longer launches on Linux. The scope rules and the start address below apply to DIY apps too.
- **What leaves the app.** A clicked link, a `target=_blank` link, Ctrl+click, middle click, Shift+click and `window.open` without window features, to an `http` or `https` URL outside the app's scope. So does a same-document navigation (`pushState`, `replaceState`) from a click, which is how sites such as Facebook follow their links; the window then goes back, as for an exclusion (see Scope rules). The scope is the manifest's `scope` (with its `scope_extensions`), the same one Chromium uses to decide when the window shows its "out of app" bar.
- **What stays.** Links within the scope; redirects, which sign-in flows go through; pages that load another page by script, also from a click handler (a sign-in button that fetches the provider's URL and loads it); form posts, also to a new tab, with or without an opener; back and forward; and popups (`window.open` with window features), which sign-in providers open and need their opener, with any link clicked in them. These keep Chromium's behavior: the page loads in the app window, with the bar that shows its origin. A URL that a user exclusion matches is the exception: it leaves by any route (see Scope rules).
- **Background or foreground.** A middle click or Ctrl+click opens the link without an activation token, so the default browser stays behind the app window, as a background tab stays behind the current one; a plain click, a `target=_blank` link, Shift+click and `window.open` hand on a token, so the browser comes to the front. The browser gets the token through the desktop portal's `OpenURI` (its `activation_token` option) or, without a portal, `xdg-open` (`XDG_ACTIVATION_TOKEN`); without one, neither the portal nor KDE's `kde-open` makes one up, even for a browser whose desktop entry has `StartupNotify=true`. Only Wayland has tokens; on X11 the window manager decides.
- **From the context menu.** A link's context menu in an app window has "Open link in default browser", which hands on a token, and "Open link in default browser in background", which doesn't, for any `http` or `https` link, also one in the app's scope. With a desktop entry for the default `https` handler (`xdg-settings get default-url-scheme-handler https`), the items name it instead, from its `Name` (for example "Open link in Floorp"), cut to 32 characters so "in background" stays in view. oganesson reads it in the background: a menu shows the last name read, reads it again, and relabels its items while open.
- **oganesson as the default browser.** The app doesn't check which browser is the default: it hands every link above to the system. If that is oganesson, the link opens in a tab of the last active regular oganesson window, never in the app window; Chromium would open a new window, as the app window is the last active one, which its workspace check misses where workspaces are unknown, as on Wayland (`patches/oganesson/core/web-apps.patch`, `GetExistingBrowserForOpenBehavior()`).
- **No prerendering in app windows.** A page activated from a prerender skips the check, so app windows don't prerender, and a tab opened in an app ("Open in app") drops the pages it prerendered (Helium's uBO keeps preloading off anyway). The e2e harness can't test this: any attached DevTools session turns prerendering off.
- **Normal tabs** are not affected.

Code: `src/chrome/browser/ui/web_applications/out_of_scope_links.cc`, hooked in by `patches/oganesson/core/web-apps.patch`. Verified by `./oganesson.py test web_app_links`.

## Scope rules

An installed app's settings page (`chrome://app-settings/<id>`) has a "Pages that stay in the app" card, where you add URL patterns to the app's scope, one per line. The rules add to the manifest's scope, except on a site a rule names.

- **Syntax.** [URLPattern](https://urlpattern.spec.whatwg.org/) strings, such as `https://*.example.com/*` or `https://accounts.example.org/login/*`. A pattern needs the scheme and host; `*` matches any text and `:name` a path segment. Regexp groups such as `(\d+)` are not supported. Parts left out match anything: `https://example.com` matches every page of that origin.
- **Narrowing.** On a host that one of the include rules names, written out with no wildcard (`https://example.com/mail/*` names `example.com`), the include rules replace the manifest's scope: with the manifest scope `https://example.com/` and that rule, only `/mail/` of `example.com` stays in the app. Rules naming other hosts still add to the scope. The rule is per host, not per origin, so a rule with any port (`http://localhost:*/...`) or scheme narrows too; a rule with a wildcard host (`https://*/login/*`, `https://*.example.com/*`) names no host and only adds, so it doesn't narrow every site it reaches. The host is compared as the matcher reads it, so `https://bücher.de/mail/*` names `xn--bcher-kva.de`. The app's start page can then be out of its scope: it opens there with the out-of-app bar, unless a start address (below) is set inside the rules.
- **Exclusions.** A pattern starting with `!` takes the pages it matches out of the scope, also pages of the manifest's scope. An exclusion wins over every other rule.
- **Exclusions are absolute.** A page in the app's own window that gets to an excluded URL by any route sends that URL to the default browser, as an out-of-scope link goes, and the window stays where it was or goes back there. Plain scope rules and the manifest's scope keep the click-only behavior above.
  - *Links, scripts and redirects.* A navigation of the page to an excluded URL, also from a script without a click, is cancelled before it loads, as is one that a redirect sends there at any hop, also the last. The window keeps its page. With a user gesture, the default browser gets an activation token and comes to the front; without one, it stays behind the app window. A form post isn't stopped, as its body can't go along, but a redirect after it is.
  - *Same-document navigations.* `pushState`, `replaceState` and fragment changes commit without a request, so the window undoes them after the fact. A pushed entry goes back, as the Back button would: the page gets a `popstate` and its router shows the page before again. The excluded entry stays as the forward entry. A replaced entry has no page before it in history, so the URL before it loads again in its place, which loses the page's state. Until then, the window can briefly show what the page drew for the excluded URL. A page that ignores `popstate` keeps showing that. One URL goes to the default browser per click or key press: a page that navigates out again after it is taken back, such as Facebook resolving a `/share/` link to the video's own URL, keeps showing that page.
  - *Not covered.* Back and Forward, reloads, and the app's launch and start address, which are not the page's own navigations. Going back and forth between two excluded entries would otherwise never end. Popups and subframes are also not covered.
- **What follows them.** Everything that uses the app's scope: links out of the app (above) and the bar that shows the origin of a page out of the app. Open app windows update that bar when the rules are saved.
- **Normal tabs.** Everything that matches a page of a normal tab to an installed app follows the rules too: the address bar's "Open in app" icon and its bubble, the app menu's "Open in <app>", the link context menu's "Open link in <app>", links that an app captures from normal tabs ("supported links"), and which app a tab's page belongs to (its notifications and badges, for example). So with the rule `https://www.facebook.com/messages/*`, "Open in app" shows on `/messages/` pages only, and never on a page an exclusion matches. A tab shows the change with its next navigation. A URL only an include rule has ranks below every app whose manifest scope has it.
- **What doesn't.** Installing and updating apps use the manifest's scope only, as does the install icon's check whether a page's app is already installed.
- **Saving.** Save checks every pattern. An invalid one is rejected with a message naming it, and the rules saved before stay. An empty card removes the rules.
- **Storage.** Per app, in the profile pref `oganesson.web_apps.user_scope_rules`. App updates and restarts keep them; they are not synced, and stay if the app is uninstalled, for a reinstall.
Code: `src/chrome/browser/web_applications/user_app_scope.cc` and `src/chrome/browser/resources/app_settings/scope_rules_item.ts`, hooked in by `patches/oganesson/core/web-apps.patch`. In normal tabs, the rules apply through `WebAppRegistrar`, whose URL-to-app matching (`FindBestAppWithUrlInScope`, `IsUrlInAppScope`, `IsUrlInAppExtendedScope`, `FindAppThatCapturesLinksInScope`, `GetAllAppsControllingUrl`) goes through `GetUserAppScopeScore()`; `WebappsClientDesktop::IsAppFullyInstalledForSiteUrl` checks the manifests' scopes only. Verified by `./oganesson.py test web_app_links`.

## Start address

The same page has a "Start address" card: the URL the app opens at, in place of the manifest's `start_url`. Empty, the field shows the manifest's start URL greyed, and the app opens there.

- **Where it applies.** Every launch that opens the app's start page: the app list, the app's desktop entry (`--app-id`), `chrome://apps`, and launches through DevTools' `PWA.launch`. They all go through `WebAppLaunchProcess::GetLaunchUrl`, where the address replaces the registrar's launch URL, and through its fallback for an out-of-scope launch URL. Launches with their own URL (shortcuts, share targets, file and protocol handlers) keep theirs. "Open in app" on a browser tab moves that tab into an app window, so it keeps the tab's page.
- **Validation.** Save accepts an http or https URL. Anything else is rejected with a message, and the address saved before stays. A launch checks the stored address again, so one of another scheme set in `about:config` is ignored.
- **Isolated web apps.** Not offered: an isolated web app and its sub-apps open at their bundle's start URL. The card is hidden for them, Save is refused, and a stored address is ignored.
- **Out of scope.** Allowed: the app opens there and shows the out-of-app bar, as for any page out of its scope. Rejecting it would make the user add a scope rule first, and a start address on another site (a sign-in page, say) is a valid choice. An app whose `launch_handler` focuses its open window (`focus-existing`) gets launches in its page's launch queue, which only takes URLs in its scope; for an out-of-scope start address, its open window navigates there instead.
- **Storage.** Per app, in the profile pref `oganesson.web_apps.user_start_urls`, kept like the scope rules: across app updates and restarts, not synced, and kept after an uninstall, for a reinstall.

Code: `src/chrome/browser/web_applications/user_app_start_url.cc` and `src/chrome/browser/resources/app_settings/start_url_item.ts`, hooked in by `patches/oganesson/core/web-apps.patch`. Verified by `./oganesson.py test web_app_links`.

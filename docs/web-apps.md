# Installed web apps

## Links out of the app

A link in an installed web app's window that leads out of the app's scope opens in the system default browser, as a link from any other desktop app does. On Linux that is what `xdg-open` opens: the desktop's default web browser.

- **Which apps.** Installed web apps (PWAs), also DIY apps: a page installed with "Install page as app…", which opens in a window as well (on Linux, "Create shortcut…" only puts a desktop shortcut to the page, which opens in a tab). Not isolated web apps, and not extension-based hosted apps, which Chromium no longer launches on Linux. The scope rules and the start address below apply to DIY apps too.
- **What leaves the app.** A clicked link, a `target=_blank` link, Ctrl+click, middle click, Shift+click and `window.open` without window features, to an `http` or `https` URL outside the app's scope. The scope is the manifest's `scope` (with its `scope_extensions`), the same one Chromium uses to decide when the window shows its "out of app" bar.
- **What stays.** Links within the scope; redirects, which sign-in flows go through; pages that navigate by script, also from a click handler (a sign-in button that fetches the provider's URL and loads it); form posts, also to a new tab, with or without an opener; back and forward; and popups (`window.open` with window features), which sign-in providers open and need their opener, with any link clicked in them. These keep Chromium's behavior: the page loads in the app window, with the bar that shows its origin.
- **Background or foreground.** A middle click or Ctrl+click opens the link without an activation token, so the default browser stays behind the app window, as a background tab stays behind the current one; a plain click, a `target=_blank` link, Shift+click and `window.open` hand on a token, so the browser comes to the front. The browser gets the token through the desktop portal's `OpenURI` (its `activation_token` option) or, without a portal, `xdg-open` (`XDG_ACTIVATION_TOKEN`); without one, neither the portal nor KDE's `kde-open` makes one up, even for a browser whose desktop entry has `StartupNotify=true` (#317). Only Wayland has tokens; on X11 the window manager decides.
- **From the context menu (#345).** A link's context menu in an app window has "Open link in default browser", which hands on a token, and "Open link in default browser in background", which doesn't, for any `http` or `https` link, also one in the app's scope. With a desktop entry for the default `https` handler (`xdg-settings get default-url-scheme-handler https`), the items name it instead, from its `Name` (for example "Open link in Floorp"), cut to 32 characters so "in background" stays in view; oganesson reads it in the background with the default-browser check below. The items are there only with the setting on and another browser the default. A menu shows the last answer, checks again, and updates its items while open; an item chosen when the latest completed check says oganesson is the default opens the link in an oganesson tab, as "Open link in new oganesson tab" does. Choosing an item starts no new check: a change of default browser after the menu's own check, with no newer check yet, takes effect from the next menu.
- **oganesson as the default browser.** If the desktop's default browser is oganesson itself (`xdg-settings check default-web-browser oganesson.desktop`), the links behave as in Chromium: a new tab or window opens in a regular oganesson window, and a plain link loads in the app window. oganesson checks this in the background whenever an app window loads a page, and uses the last answer; until the first answer it assumes another browser is the default.
- **No prerendering in app windows.** A page activated from a prerender skips the check, so app windows don't prerender, with the setting on or off (it can be turned on while a prerendered page waits), and a tab opened in an app ("Open in app") drops the pages it prerendered (Helium's uBO keeps preloading off anyway). The e2e harness can't test this: any attached DevTools session turns prerendering off.
- **Normal tabs** are not affected.
- **Turning it off.** The pref `oganesson.web_apps.open_out_of_scope_links_in_default_browser` in `about:config` (on by default, one setting for all apps).

Code: `src/chrome/browser/ui/web_applications/out_of_scope_links.cc`, hooked in by `patches/oganesson/core/pwa-external-links.patch`. Verified by `./oganesson.py test web_app_links`.

## Scope rules

An installed app's settings page (`chrome://app-settings/<id>`) has a "Pages that stay in the app" card, where you add URL patterns to the app's scope, one per line. The rules add to the manifest's scope, except on a site a rule names.

- **Syntax.** [URLPattern](https://urlpattern.spec.whatwg.org/) strings, such as `https://*.example.com/*` or `https://accounts.example.org/login/*`. A pattern needs the scheme and host; `*` matches any text and `:name` a path segment. Regexp groups such as `(\d+)` are not supported. Parts left out match anything: `https://example.com` matches every page of that origin.
- **Narrowing (#346).** On a host that one of the include rules names, written out with no wildcard (`https://example.com/mail/*` names `example.com`), the include rules replace the manifest's scope: with the manifest scope `https://example.com/` and that rule, only `/mail/` of `example.com` stays in the app. Rules naming other hosts still add to the scope. The rule is per host, not per origin, so a rule with any port (`http://localhost:*/...`) or scheme narrows too; a rule with a wildcard host (`https://*/login/*`, `https://*.example.com/*`) names no host and only adds, so it doesn't narrow every site it reaches. The host is compared as the matcher reads it, so `https://bücher.de/mail/*` names `xn--bcher-kva.de`. The app's start page can then be out of its scope: it opens there with the out-of-app bar, unless a start address (below) is set inside the rules.
- **Exclusions.** A pattern starting with `!` takes the pages it matches out of the scope, also pages of the manifest's scope. An exclusion wins over every other rule.
- **What follows them.** Everything that uses the app's scope: links out of the app (above) and the bar that shows the origin of a page out of the app. Open app windows update that bar when the rules are saved.
- **Saving.** Save checks every pattern. An invalid one is rejected with a message naming it, and the rules saved before stay. An empty card removes the rules.
- **Storage.** Per app, in the profile pref `oganesson.web_apps.user_scope_rules`. App updates and restarts keep them; they are not synced, and stay if the app is uninstalled, for a reinstall.
- **Not covered.** Opening links from normal tabs in the app ("supported links") still uses the manifest's scope only.

Code: `src/chrome/browser/web_applications/user_app_scope.cc` and `src/chrome/browser/resources/app_settings/scope_rules_item.ts`, hooked in by `patches/oganesson/core/pwa-user-scope.patch`. Verified by `./oganesson.py test web_app_links`.

## Start address

The same page has a "Start address" card: the URL the app opens at, in place of the manifest's `start_url` (#346). Empty, the field shows the manifest's start URL greyed, and the app opens there.

- **Where it applies.** Every launch that opens the app's start page: the app list, the app's desktop entry (`--app-id`), `chrome://apps`, and launches through DevTools' `PWA.launch`. They all go through `WebAppLaunchProcess::GetLaunchUrl`, where the address replaces the registrar's launch URL, and through its fallback for an out-of-scope launch URL. Launches with their own URL (shortcuts, share targets, file and protocol handlers) keep theirs. "Open in app" on a browser tab moves that tab into an app window, so it keeps the tab's page.
- **Validation.** Save accepts an http or https URL. Anything else is rejected with a message, and the address saved before stays. A launch checks the stored address again, so one of another scheme set in `about:config` is ignored.
- **Isolated web apps.** Not offered: an isolated web app and its sub-apps open at their bundle's start URL. The card is hidden for them, Save is refused, and a stored address is ignored.
- **Out of scope.** Allowed: the app opens there and shows the out-of-app bar, as for any page out of its scope. Rejecting it would make the user add a scope rule first, and a start address on another site (a sign-in page, say) is a valid choice. An app whose `launch_handler` focuses its open window (`focus-existing`) gets launches in its page's launch queue, which only takes URLs in its scope; for an out-of-scope start address, its open window navigates there instead.
- **Storage.** Per app, in the profile pref `oganesson.web_apps.user_start_urls`, kept like the scope rules: across app updates and restarts, not synced, and kept after an uninstall, for a reinstall.

Code: `src/chrome/browser/web_applications/user_app_start_url.cc` and `src/chrome/browser/resources/app_settings/start_url_item.ts`, hooked in by `patches/oganesson/core/pwa-user-start-url.patch`. Verified by `./oganesson.py test web_app_links`.

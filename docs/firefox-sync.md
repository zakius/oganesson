# Firefox Sync

Sync is shared with tennessine through dubna: its C++ adapters (`dubna/src/chrome/browser/firefox_sync/`) connect Chromium's password, bookmark, history and autofill stores to `dubna/rust/oganesson_sync`. Desktop's side, the tabs adapter and the account on the profile, implements dubna's `firefox_sync_platform.h` in `src/chrome/browser/firefox_sync/platform/`. The Rust library uses pinned Mozilla application-services crates for account and Sync protocols. It loads beside the browser as `liboganesson_sync.so`, using the browser's NSS, or on Windows as `oganesson_sync.dll`, with its own NSS ([Windows](windows.md)).

The retained implementation uses OAuth with PKCE, encrypts saved account secrets through Chromium's OS cryptography service, and routes HTTP through the profile's network context. Signing out discards pending results. The client must honor server backoff and preserve local edits made during a sync.

Supported implementation scope: passwords, bookmarks, history, open tabs, addresses, payment methods, and containers (below). Bookmark keywords and separators stay in the Sync store (places) only: the browser never sees them, and Sync keeps them in place for Firefox. While Settings → Privacy → "Don't save browsing history" (`history.saving_disabled`) is on, history doesn't sync: its switch is off and greyed out, and a sync under way when it is turned on applies no history.

Other devices' open tabs show where Chromium shows synced tabs: History → Tabs from other devices (linked from the Sync settings), the app menu's History → Recent tabs, and the `chrome.sessions` API. dubna's `remote_tabs.cc`, shared with tennessine, turns them into Chromium's synced sessions, one window per device, and dubna's `firefox-sync-remote-tabs.patch` lets the `SessionSyncService` return them while Chromium's own tab sync is off. `oganesson/core/firefox-sync-remote-tabs.patch` links History and the app menu to them. Tab search doesn't list other devices' tabs.

Tabs go between devices as in Firefox, through Mozilla accounts' device commands rather than the sync server. "Send to device ▸" in the page, link and tab context menus lists the account's other devices that take tabs, Firefox ones included, and "All devices" (`src/chrome/browser/firefox_sync/platform/send_to_device_menu.cc`, wired in by `oganesson/ui/send-to-device.patch`). A tab another device sends opens in the background, with a system notification that switches to it. A request from Firefox to close tabs here closes every open tab at a URL it names: Firefox names tabs only by URL. In History → Tabs from other devices, each tab of a device that takes such requests has a close button (`oganesson/ui/close-synced-tab.patch`); the tab stays hidden until that device's next sync. A sent tab goes out at once. Tabs and close requests for this browser arrive at once through Mozilla's push server, as in Firefox: while signed in, `src/chrome/browser/firefox_sync/platform/push_connection.cc` keeps one connection to it (autopush's WebSocket protocol, a ping every 30 minutes, reconnecting with growing waits), and dubna registers its endpoint with the account. A notice only starts a fetch; its payload is never decrypted. Settings → Sync → Receive tabs instantly turns the connection off. They are also fetched with each sync, when a window of the profile comes to the front (at most once a minute), and every 15 minutes, which Settings → Sync can change to 30 or 60, or to only with each sync. They wait on the accounts server for up to 28 days, so a later fetch loses none.

The account shows like a Google one would: `desktop_platform.cc` gives the browser profile the Mozilla account's name and picture (Chromium's GAIA name and picture fields), so the avatar button, the profile menu and the Sync settings card show them. `oganesson/ui/firefox-sync-avatar.patch` keeps them across restarts and shows "Sync paused" on the avatar button while the account must sign in again.

## Containers

Firefox has no Sync collection for containers. Mozilla's Multi-Account Containers add-on (Gecko ID `@testpilot-containers`) syncs them through its `storage.sync` area, which Firefox Sync carries in the `extension-storage` collection, one record per add-on. oganesson reads and writes the same records, so a Firefox profile with the add-on and the browser show the same containers and site assignments. The type is "Containers" in Settings → Sync.

- **Engine.** dubna's `extension_storage.rs` owns the `extension-storage` collection, over application-services' `webext-storage` store (`firefox_sync_extension_storage.db` in the profile) and engine, which Firefox runs too. It is the collection's only engine: when Firefox add-ons get their own `storage.sync` data, their areas go through it as well. Until then it stages only the add-on's area; other add-ons' records stay as they came. `mac.rs` maps the area; `containers_adapter.cc` (dubna) applies its ops to the `containers.list` and `containers.traffic_control` prefs.
- **Format** (the add-on's `sync.js` and `assignManager.js`). `identity@@_<uuid>` per container (`name`, `icon`, `color` in the names Firefox used before 153, `cookieStoreId`, `macAddonUUID`), `siteContainerMap@@_<host>` per site assignment (`userContextId`, `neverAsk`, `identityMacAddonUUID`, `hostname`), `deletedIdentityList`, `deletedSiteList`, and a `MACinstance:<uuid>` key for this install, which lists what it has, so the add-on keeps a deletion in the lists until the browser has seen it. Fields the add-on wrote are kept.
- **Identity.** Container ids differ on each device, so containers match by the add-on's uuid. The engine state keeps the uuid of each container. On a first sync, a container matches one of the area with the same name, as the add-on matches them, so Personal, Work, Banking and Shopping don't double and keep their cookies. A container whose id is a uuid (Settings makes those) goes up with its id; one from Firefox gets its uuid as id here. Temporary containers never sync, nor does the containers' order.
- **Sites.** A site assignment is a Traffic Control rule that is enabled, opens a container of the list, and has the single pattern `.<host>` or `.<host>:<port>`: that host only, as the add-on matches it. A rule for `example.com` with its subdomains, other patterns or paths, a temporary container or none, or a rule switched off, stays local and sync never changes it. A site assignment from Firefox becomes such a rule at the end of the list. The add-on glues a non-default port to the host (`localhost8080`): the digits after a host name are its port, and the rule is `.localhost:8080`. An IPv4 address with a port can't be split again, so such keys stay on the server, and rules for ports 80 and 443, which the add-on leaves out of its keys, stay local. The area must stay under `storage.sync`'s quota (100 KB, 8 KB per key, 512 keys), which the store enforces: new site assignments that would take it over stay local, the last hosts first, and the type's status says how many.
- **Conflicts.** Each sync compares the browser's containers and rules with the state it saved after the last sync it applied, and only the differences go up. A change Firefox made that the browser never applied (it quit before, or the upload failed) therefore comes down again on the next sync, rather than being taken for a local edit (oganesson-core#40). When both sides changed one key, Firefox's wins, as in the add-on. A deletion in Firefox removes the container here, with its tabs and storage; one here goes into `deletedIdentityList`, and stays deleted here even if a Firefox that hadn't seen it yet uploads it again.
- **When.** Only when meta/global lists `extension-storage`, which Firefox does while "Add-ons" is on in its Sync settings; until then the type shows why it can't sync. Firefox applies the records only with Multi-Account Containers installed and its "Sync containers" option on.

`python3 tools/check_firefox_sync.py` exercises the built library against the local fake server. `./oganesson.py test firefox_sync` exercises the browser path. These checks must pass on the extracted build. They are not evidence of a real Mozilla-account test.

Before using this build with personal data, verify sign-in and two-way additions, edits, deletions, restart, and sign-out with a dedicated Mozilla test account and Firefox/Fenix. The original source documented no completed real-account verification and used an example application's OAuth client ID. Review that client identity before distribution. Use a fresh browser profile for validation.
